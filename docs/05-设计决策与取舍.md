# 05 · 设计决策与取舍

本文档记录系统背后几个关键技术选型的理由，帮助你在自己的场景里做判断。

## 一、在线多维表格是结构化库，不是非结构化存储

- 个人库（在线多维表格）是**结构化**的：有表 / 记录 / 字段、固定 schema，不是非结构化的自由文本。
- 它是「富类型表格库」——字段类型丰富（单选、多选、日期、附件、人员、关联、公式、lookup），用关联字段近似外键与 JOIN，弱化范式，用视图/界面/API 而非 SQL，schema 可随时改。
- 非结构化数据（无固定 schema，如整篇文档、图片、音视频）不适合作为本系统的主数据。

## 二、访问在线库走应用层 API，而非数据库连接

访问在线多维表格不是「数据库连接」，而是**应用层 REST API**：

- 端点是一组 HTTP URL，不是 `host:port` 连接串；不能写 SQL、不能跨表 JOIN、看不到物理表。
- 认证用 OAuth2 **Bearer Token**（带过期和 scope 授权），不是数据库用户名/密码。
- 多租户隔离：物理上共享大规模分布式集群（分片、多副本、高可用，用户不独占实例），逻辑上按**组织（租户）＋ 文档资源 ＋ 权限 ACL** 隔离。
- 类比：更像调用 Salesforce / Airtable 的 REST API，而不是用客户端直连 Oracle。

## 三、为什么不建议「在云盘里放一个 sqlite」

一个常见想法是把 sqlite 文件丢进网盘同步，当作云端数据库。这通常不成立：

- **云盘不是数据库服务器**：sqlite 是单机嵌入式文件库，没有网络服务；上传到云盘只是静态文件，无法被远程 SQL 访问，要读写必须先下载、改完再上传。
- **文件级同步会损坏 sqlite**：网盘是文件级同步、不是数据库协议；多端并发改会产生冲突副本。sqlite 靠文件锁处理并发，文件级同步/挂载会让锁失效，导致 `database is locked` 甚至库损坏。
- **sqlite 给的是引擎，不是应用**：它没有手机端 UI、没有看板/日历/表单/筛选视图、没有多用户和权限——这些正是闲时引擎需要的呈现层，全要自研。
- 想让「云端 sqlite」成立，需要上托管数据库（如 Turso / Cloudflare D1 / 云 MySQL/PostgreSQL）+ 自写 API、认证、多端 UI，等于把现成多维表格的能力从零再造，成本远大于收益。

## 四、本地库 vs 云端库的分工

一个经过验证的分工方式：

| 维度 | 本地工作库（如 sqlite） | 云端个人库（多维表格） |
|---|---|---|
| 定位 | 独占、离线、强 schema | 多端、开箱即用 |
| 优势 | 与本地业务语料同处一个记忆，分析口径一致 | 视图/看板/日历/表单/权限/API 免开发 |
| 侧重 | 一致性 | 呈现与可达性 |
| 短板 | 云端不可随时达，靠待调和机制弥补 | 不能写任意 SQL、不能跨库 JOIN |

**取舍逻辑**：用本地优先换上下文一致性，用云端表格换多端可达与免开发的呈现层；两者通过「提醒指针 + 待调和信箱」关联，而不是互相拷贝。

## 五、几条被验证的小决策

- **只增不删**：删除会永久损失可分析性；用状态标记替代删除，只有误录才删。
- **跑通与打磨分条**：未知摸索与已知手工是两种活，混在一起会让打磨没有终点。
- **兴奋点先不参与排序**：数据量不足时，这类字段只攒着、用于后续画像，不进入早期推荐排序。
- **默认最短时长 + 「任何」场景**：把字段标大、场景标窄，会让条目永远等不到合适的时机。
- **单端运行优先**：如果某一端访问数据有明显摩擦，而另一端已覆盖手机和电脑，就先在摩擦小的一端跑，避免为双端同步付出额外成本。
