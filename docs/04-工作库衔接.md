# 04 · 工作库衔接（个人库与工作库分离）

> 当一个人既想管理「自己的想做」，又需要承接「别人下达的工作任务」时，把两类信息混在同一个池子里会污染画像。本文档给出一套分离但关联的机制。
>
> 以下为通用方法论，不包含任何真实任务、人名或客户信息。

## 一、为什么分开：按「意图归属」分库

- **个人库**装「我自己的意图」：我的想法、我的待办。
- **工作库**装「下达者的意图」：由他人（如管理者/客户）下达的任务，本体独立存放。

分开的根本原因是**画像的准确性**：

- 工作任务的出发点不是我，是下达者。若混进个人库，个人画像会被他人意图污染，无法准确表达我的个人工作意图。
- 反过来，工作库本身能画出**下达者的画像**——他关注什么、如何决策、优先级如何排布。

一句话：**个人库画「我」，工作库画「下达者」；钩子负责把两者关联，却不让它们互相污染。**

## 二、两类指针

个人库里与工作任务相关的条目，分两种：

- **提醒指针（只读）**：如「推进 工作编号-XXX 某任务」——只用于提醒自己，不改工作库的任务状态。
- **同步意图（写意图）**：当某工作任务有进展 / 状态变化 / 结案时，不当普通备忘，按格式单独记一条，打上「业务同步」标记。

### 同步意图记录格式（一条一行）

```
工作编号 ｜ 变更类型（进展/状态/结案/新任务）｜ 内容与依据 ｜ 在何场景说的 ｜ 日期
```

- 新任务还没有编号时写「工作-新」，由调和方分配正式编号。

## 三、只记录，不宣称已生效

记录同步意图后，应告知「**已记为待同步意图，回桌面后由能访问工作库的助手调和进工作库生效**」，而不是说「已结案完成」。

## 四、调和机制（带版本校验）

1. 移动端/云端侧先捕获意图，写入「待同步」信箱。
2. 回到工作库所在的设备后，能访问工作库的助手读取待同步条目，**带版本校验**写入工作库。
3. 再把已调和的条目标记「已同步」，**原文保留、不删除**。

### 为什么需要版本校验

多个端都可能写同一个工作库，写入前先校验版本，可避免覆盖他人的更新、防止冲突。

## 五、两个个人库相互隔离、永不直接同步

如果系统在不同平台各有一个个人库，它们**不互相拷贝**——这是设计使然。跨侧信息只通过工作库流动：

- 共享库不会把数据再推回个人库。
- 各端之所以一致，是因为都以工作库为准读同一份工作状态。
- 流向是「意图 → 调和 → 工作库生效」，不是个人库互相同步。

## 六、纯个人事项照旧

购物清单、灵感、闲时安排正常处理，不加工作编号、不打「业务同步」标签。

## 七、工作库放本地还是云端：一个典型取舍

工作库可以放本地（某台固定设备上的一个文件），也可以放云端。选择本地的典型理由：

- **业务语料在本地**：各端是在本地会话里学习业务文件，工作库任务与这些本地文件匹配。
- **放云端会割裂上下文**：库一旦在云端，就和本地的任务读取、学习不在同一个会话里，无法直接关联印证。
- **放本地便于业务分析**：任务与本地业务逻辑同处一个记忆，可相互引用、比对。
- **取舍**：用「本地优先」换上下文一致性；牺牲的「云端随时可达」由**待调和意图机制**弥补——先在移动端捕获意图，回到本机再调和生效。

## 八、完整闭环

```
个人侧捕获 → 记为待同步意图（信箱）→ 回工作库所在设备
          → 带版本校验写入工作库 → 回填提醒指针编号、信箱条目标「已同步」（原文保留）
```
