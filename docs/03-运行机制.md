# 03 · 运行机制

## 机制一：录入（摩擦必须极低）

- 用户**只需说事项本身**，其余字段由助手自动补全。
- **不要追问字段**。没把握就填默认值，不要为了填全而卡住。
- 支持一次丢一批，批量录入。
- **默认姿势：先写「任何」和最短时长。** 拿不准时长就写 5 分钟，拿不准在哪做就写「任何」。
- 只有确实非坐定不可的事（跑脚本、装模型、剪片子）才标「电脑前」。标大了，它就永远等不到整块时间。

> 录入摩擦是这个系统第一号的死因。摩擦一高，就懒得记，池子就喂不饱。

### 跑通与打磨，分两条记

工作流性质的事，「跑通」和「打磨」是两种活：

- **跑通**＝未知的摸索，要整块时间、精力高、能试错；一旦走通，本条直接标 `done`。
- **打磨**＝已知的手工活，碎片时间、精力低也能动；另起一条「打磨 XXX」承接。

混在一条里，打磨没有终点，这件事永远不被认可。

## 机制二：查询（触发词「闲了」）

说「闲了」时可以带参数（如「闲了，10 分钟，手机上」「闲了，只想弄家里的事」）。助手要：

1. **先按情境筛**：时长 / 精力 / 场景。
2. **再按价值排**。
3. **只回 1–3 件**，绝不给长串——选择太多本身也是启动成本。
4. 建议里可以带一句可行性提示（先问谁、先从哪查）。
5. **提议完等用户拍板，不自己动手。**

### 关键规则：场景不做减法

出场条件 = 用户当前状态 **或** 条目任一场景标签，命中其一即可推。

- 不去「判断此刻用哪台设备」——猜错就是漏掉，而漏掉正是要治的病。
- 场景标签只在两处起作用：① 两条价值相当时，命中当前状态的多推一点；② 条目**只有**「电脑前」一个标签、且用户明说此刻不在电脑前，才降权。**降权不是隐藏**，照样可以被推荐，只是排在后面。

**价值 ≠ 紧急。** 排序按长期真正在乎什么，不按谁催得急。

### 复活是正常操作

`done` 的事以后又要做：状态改回 `active`，**清空完成日期**，并在备注追加一行 `yyyy-MM-dd 复活：<原因>`，同时校一遍场景/时长是否过时。不新建条目。被错标 done 的改回即可，不算复活、不用写理由。

## 机制三：周回顾（不做这步，池子会变成垃圾场）

每周一次，每条问三个问题：

1. **还想做吗？** → 不想，标 `放弃`（不是删掉）。
2. **现在能做吗？** → 不能，移到 `someday`。
3. **一直没做为什么？** → 太模糊就拆小，太难就降级，缺渠道就先记一条跟进。

**积压超过 30 天且没动过的，主动问还要不要。** 说「不做了」标 `放弃`，说「先放着」标 `someday`，说「还想做」就留着。但都不删。

> 一个池子被信任的前提不是干净，是它记的每一条都还在。平时说了「做完了」就该当场改，不要攒到周末。

## 特色子系统一：灵感保险箱

有些 `someday` 不是「现在做不了」，而是**「还没想清楚从哪下手」**——这类最需要被提醒，因为灵感不主动提醒就真的丢了。

- **判定方法**：价值=中 + 时长在 5 分钟量级 + 备注里写了「怎么提醒」→ 跳过 `someday` 的屏蔽，在「闲了」时浮上来。
- **固定话术**：「现在可以考虑一下这件事要怎么做了」——只要求想出第一步，不要求做完、不要求写文档。
- **为什么设成 5 分钟**：目标只是「开始思考」，门槛必须极低。

## 特色子系统二：触发式清单（采购/地点）

购物、办事这类条目标状态为 `触发`，**永不参与「闲了」排序**。否则每次问「闲了」都被购物清单淹没，真正重要的事就看不见了。

- 当用户**主动报出情境**时（如「我去趟超市」），才把这些调出来，而且**一次列全，不砍到 1–3 条**。
- 地点从用户话里取，**拿不准就留空，绝不瞎猜**。
- **不替用户勾采购项。** 勾没买到是用户自己的事——代勾会把没买到的东西静默抹掉；未勾的天然留到下次到该地点再提醒。

## 多端协作纪律

- 会话不是记忆，云端数据表才是；任何新口径第一时间写进协议正文，不留在对话里。
- 写完回读一次再确认；协议与数据冲突以协议为准并改回数据。
- 同一件事不录两份，发现重复就补充原条目；但不把两条不同的事硬合并。
